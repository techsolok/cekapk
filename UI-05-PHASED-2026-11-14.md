## 1. Audit findings

### 1.1 App hubs — the search gap

| | `/aplikasi` (ID) | `/en/aplikasi` (EN) |
|---|---|---|
| Filtering | Server-side `?q=` already works: `name + developer + tagline + categoryName` (+ `searchAliases` lookup, e.g. "bilibili" → bstation) | Server-side `?q=` already works: `base.name + base.developer + en.taglineEn + categoryNameEn(...)` — English-only fields |
| Results line | "Hasil pencarian untuk …: N aplikasi ditemukan" + "Tampilkan semua 50 aplikasi" link | "Search results for …: N apps found" + "Show all 11 apps" link |
| Empty state | "Tidak ada aplikasi yang cocok…" + link to full catalog | "No apps match…" + link to all English guides |
| On-page search input | **NONE** — users could only reach `?q=` via the homepage SearchBox or the header "Cari" pill | **NONE** — search worked only via the `?q=` URL parameter |
| Cards / sorting / content | Unchanged by this phase | Unchanged by this phase |

The gap was the input, not the filtering. Both hubs already had the results-count line, the clear (show-all) link, and the empty state. The existing homepage `SearchBox` component was NOT reused: it is an autocomplete jump-box that calls `/api/search` and navigates straight to one result — the wrong pattern for a hub that filters its own catalog in place, and its API is Indonesian-only, so it would return wrong-language results on the English hub.

### 1.2 English limitation (brief Task A requirement 8) — resolved, not a blocker

The English catalog **can** support accurate localized search: the EN `?q=` filter already searches English-only fields (name, developer, English tagline, English category name) across the 11 apps with an English edition. The search box was therefore added to the English hub too.

**The limitation that remains (and is stated on the page itself):** only 11 of the 50 catalog apps have an English edition. The other 39 apps are Indonesian-only and are not searchable from `/en/aplikasi`. The hub intro already discloses this ("The full catalog of 50 apps lives in the Indonesian edition"). No English search over Indonesian fields was added — that would have returned results the English reader cannot read.

### 1.3 FactBox — reuse already exists

Both app detail pages import the **same** `FactBox` from `@/components/ui` (ui.tsx:78, 11 lines, `rows: { label, value }[]`):

- ID page: `src/app/(id)/aplikasi/[slug]/page.tsx:102` — 7 rows (Versi, Ukuran, Android Minimum, Kategori, Bahasa, Harga, Terakhir Dicek).
- EN page: `src/app/(en)/en/aplikasi/[slug]/page.tsx:100` — 6 rows (Developer, Category, Price, Minimum Android, Languages, Last checked), values localized via `src/lib/data/i18n-en-factbox.ts` (whose mapping completeness is pinned by check:seo).

There is **no duplicated FactBox markup to remove** — the shared component already exists, and language-specific labels, values, optional rows, and ordering are preserved by passing different rows per page. No change was made to FactBox itself, to either app detail page, to app data, or to JSON-LD.

### 1.4 The one remaining duplication — proposed, NOT implemented

The compatibility `<dl>` is copy-pasted in both app detail pages with **identical** wrapper and cell classes:

- `src/app/(id)/aplikasi/[slug]/page.tsx:165` — "Kompatibilitas & Informasi Teknis"
- `src/app/(en)/en/aplikasi/[slug]/page.tsx:136` — "Compatibility & Technical Info"

```html
<dl className="grid gap-px overflow-hidden rounded-2xl border border-mist bg-mist sm:grid-cols-2">
  <div className="bg-paper p-3"><dt className="text-xs font-medium text-muted">…</dt><dd className="mt-0.5 text-sm font-semibold text-ink">…</dd></div>
```

## 2. Implementation (Task A)

A plain HTML GET form, added to both hub pages directly under the H1. It reuses the existing server-side `?q=` filter — no new URL scheme, no client JavaScript, no new data, no new fields.

**Indonesian** (`src/app/(id)/aplikasi/page.tsx`):

```jsx
<form method="get" action="/aplikasi" role="search" className="space-y-2">
  <label htmlFor="cari-katalog" className="block text-sm font-semibold text-ink">Cari aplikasi di katalog</label>
  <div className="flex gap-2">
    <input id="cari-katalog" name="q" type="search" defaultValue={q}
      placeholder="Cari aplikasi… misalnya TikTok, DANA, Roblox"
      className="min-h-[52px] min-w-0 flex-1 rounded-2xl border border-ink/10 bg-paper px-4 text-base text-ink shadow-sm outline-none focus:border-primary" />
    <button type="submit" className="min-h-[52px] shrink-0 rounded-xl bg-primary px-6 font-semibold text-white shadow-sm">Cari</button>
  </div>
  {query ? (<p><Link className="text-sm font-semibold text-linkblue" href="/aplikasi">Bersihkan pencarian</Link></p>) : null}
</form>
```

**English** (`src/app/(en)/en/aplikasi/page.tsx`): same structure, `action="/en/aplikasi"`, `id="search-catalog"`, label "Search the app catalog", placeholder "Search apps… e.g. TikTok, DANA, Roblox", button "Search", clear link "Clear search".

Styling reuses existing site patterns: input from the homepage SearchBox, submit button from the tool pages (`TiktokTool`). The input is pre-filled with the current query (`defaultValue={q}`); the clear link appears only while a query is active (the results-count line's existing "Tampilkan semua / Show all" link is kept as well).

**What was deliberately NOT changed:** the `?q=` filter logic (both hubs), `searchAliases`, `SearchBox`, the homepage, the header "Cari" pill, the EN header (no search pill — Phase B decision stands), `AppCard`, catalog data, metadata/canonical/hreflang/robots/sitemap/JSON-LD, `AnalyticsConsent.tsx`, `SiteChrome.tsx`, any API/backend/auth/download code, any dependency. No new routes. No search-volume or keyword claims were introduced.

**Why not client-side instant filtering:** the server `?q=` filter is the site's established search pattern (it is the WebSite `SearchAction` target in the JSON-LD on both homepages), it is already tested, and duplicating its logic in a client component would risk the two filters drifting apart. A GET form keeps exactly one filter.
